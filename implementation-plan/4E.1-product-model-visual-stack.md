# 4E.1 Correction — ProductModel Visual Stack

Status: **direction frozen** (supersedes ChoiceValue-first-as-entire-visual-state)
Depends on: 4E runtime composition
Does not start: 4F

## Correction

`ChoiceValue` must **not** be the source of all visual state.

A product must already have a valid, meaningful visual presentation before configuration-specific overrides are applied.

## Frozen visual stack

```text
ObjectAssetRevision
→ immutable raw visual baseline

ProductModel
→ product-specific static visual setup

Selection-driven VisualBindings
→ optional overrides

        ↓
VisualState
        ↓
Three.js
```

### Ownership questions

| Layer | Question |
| --- | --- |
| ObjectAssetRevision | What did the reusable asset ship with? |
| ProductModel | What should this product normally look like? |
| VisualBinding | What changes because of configuration? |

## Empty selection semantics

```text
{}
```

must mean:

```text
ProductModelDefaultVisualState
= ObjectAsset baseline
+ ProductModel static setup
```

**Not** necessarily raw GLB baseline alone.

Internally, raw GLB / ObjectAsset baseline remains required for deterministic reconciliation and restoration. Semantically, the product default may differ from the asset raw default.

Shopper selection then layers:

```text
ObjectAsset baseline
        ↓
ProductModel static setup
        ↓
Selection overrides
        ↓
VisualState
```

## VisualSetup vs VisualBinding

Keep static setup separate from `VisualEffect` if `VisualEffect` means “activated by a ChoiceValue.”

Conceptual ProductModel:

```text
ProductModel
├── ModelTargets
├── VisualSetup[]      ← always active for this ProductModel
└── VisualBindings[]   ← activated by semantic Selection
```

Shared operation vocabulary (same ops, different activation):

```text
SET_MATERIAL
SET_VISIBILITY
REPLACE_COMPONENT
```

Do **not** invent a second rendering model.

## Runtime

```text
deriveVisualState(
  baseline,
  staticSetup,
  bindings,
  selection
)
```

Precedence (layer order — no priority numbers):

```text
baseline
< static setup
< active configuration overrides
```

## Editor authoring split

Same scene. Same targets. Same assets. Same operations. Different intent:

```text
MODEL
"What does this product normally look like?"
→ author VisualSetup[] (+ targets / assets as needed)

CONFIGURATION
"What changes when shoppers configure it?"
→ author ChoiceValue → VisualBindings[]
```

The ChoiceValue-first coverage UI remains valid for **CONFIGURATION**, not as the sole visual IA.

## Invariants (freeze)

1. **A ProductModel must be renderable and visually meaningful with zero Choices and zero VisualBindings.**

2. **Configuration modifies product visual state; it does not construct the product's entire visual state from nothing.**

3. Editor state remains a projection of persisted CubeCom state — not a second domain source of truth.

4. Reuse one `deriveVisualState` in `@repo/product-graph` — no editor fork.

## Current gap (as of ChoiceValue-first 4E.1 UI)

| Exists today | Missing |
| --- | --- |
| ObjectAssetRevision baseline capture | `VisualSetup` persistence / GraphQL |
| Selection `VisualEffect` / bindings | Always-on static setup apply in derive |
| `{}` → restore capture baseline (≈ raw after mount) | `{}` → baseline + static setup |
| CONFIGURATION-oriented editor panels | MODEL authoring workspace for VisualSetup |

## Implementation slices (when approved)

### Slice A — Contract + derive
- Introduce `VisualSetup` (or equivalent) on ProductModel
- Extend `deriveVisualState` with `staticSetup` layer
- Empty selection tests: meaningful default ≠ raw-only when setup present
- Resolve / editor hydrate consume the same derive

### Slice B — MODEL authoring
- Editor workspace: MODEL vs CONFIGURATION
- Author VisualSetup with same ops + target picking
- Preview Selection remains explicit; MODEL edits are always-on

### Slice C — Persist / reload proof
- Save setup + bindings independently
- Hard reload: same default scene with `{}`, same overrides with selection
